# Heat v2 - the definitive heat catalog

Goal: EVERY spot in the world with heat40 >= 12, found from first principles, with the seed-sampling noise
measured and built into every cutoff. Replaces heat v1 (archived: `the original working copy, NOT SHIPPED`, kept
only as test data). Rules (project owner, 2026-09-21): no full brute-force 2D scan; re-derive where heat can exist
from the ground up; re-running spots already hunted is fine.

## Scope - EVERY location inside the 30M world border (project owner, 2026-09-21)

The catalog covers the whole world, not a region or a ranked subset: every chunk column AND every chunk row
from **-1,874,999 to +1,874,999** (blocks -29,999,984 to +29,999,999; 3,749,999 x 3,749,999 chunks). Every
phase must span that full range on its axis - the phase 2 row files already do (3,749,999 rows each), and the
phase 3 column scans must too (`--heat-from -1874999 --heat-to 1874999`). No cross product of "top" lists,
no cut to a hot corner: that is exactly how v1 missed half the heat-22+ spots.

Border caveat, to flag in the catalog rather than drop: a spot within 8 chunks of the border has part of its
heat disc (and of any farm window) outside the border, where mobs do not spawn - heat is computed as if the
world continued, so those spots are marked `near_border` for checking, never silently removed.

## The pattern, in equations (2026-09-21)

Slime test (Java): chunk (x, z) is slime for world seed S iff `Random(S + X(x) + Z(z) ^ 0x3ad8025f).nextInt(10) == 0`, with
    X(x) = int32(x^2 * 0x4c1906) + int32(x * 0x5ac0db),     Z(z) = int32(z^2) * 0x4307a7 + int32(z * 0x5f24f).
Java Random keeps 48 bits: t = (S + X + Z) ^ 0x3ad8025f ^ M mod 2^48, M = 0x5DEECE66D; B = ((t*M + 11) mod 2^48) >> 17
(31 bits); slime iff B mod 10 == 0, i.e. B even AND B mod 5 == 0.

1. Split the seed: S = s + 2^35 v (s = low 35 bits, v = top 13). Then B(v) = B(0) + 2^18 w (mod 2^31), w = M v mod 2^13,
   the SAME w for every chunk. So for one s: a chunk is POSSIBLE iff B(0) is even; its PHASE is p = B(0) mod 5; it is
   slime at w = p (mod 5) while w < 8192 - (B(0) >> 18), and at w = p + 2 (mod 5) after that (the 2^31 wrap).
   Consequence: all 8,192 seeds of a class move in lockstep (the phase model; exact, 0 mismatches in 90.9M checks).
2. Possibility is bit 17 of t*M + 11, which depends only on t mod 2^18, i.e. on (S + X(x) + Z(z)) mod 2^18.
3. Heat. heat40(cx, cz) = P_S[ >= 40 of the 197 chunks within radius 8 of (cx, cz) are slime ] / 2.1e-5 (1 = a random
   place). Adding a constant to every chunk's offset is absorbed by the uniform seed, so heat depends only on the
   difference vectors  dX_d = X(cx + d) - X(cx)  and  dZ_d = Z(cz + d) - Z(cz),  d = -8..8.
4. Exact periods of the possibility pattern (checked: 2,000/2,000 at the period, 0/2,000 at half of it):
       dX_d(x + T) - dX_d(x) = 0x4c1906 * 2 T d  (mod 2^18)  -> 0 for all d iff T = 0 mod 2^16   (0x4c1906 = 2 x odd)
       dZ_d(z + T) - dZ_d(z) = 0x4307a7 * 2 T d  (mod 2^18)  -> 0 for all d iff T = 0 mod 2^17   (0x4307a7 odd)
   (int32 truncation only touches bits >= 32.) So which chunks CAN be slime tiles the world with a 65,536 x 131,072
   torus. Heat is not exactly periodic because the phase (mod 5) uses all 48 bits: sister columns 65,536 apart keep a
   hot spot hot 98% of the time, sister rows 131,072 apart 93-94%, sister PAIRS only ~66% (log sd 0.22-0.27).
5. Z lines (measured, not derived): every row with heat >= 12 at 4 reference columns lies within 4 rows of
   cz = 48.5 + 96.875 n (= 48.5 + 3100 n / 32; 131,072 / 96.875 = 1,353 lines per Z period); mean heat by offset from
   the line centre: 10.3 at 0, 8.2 at +-2, 4.3 at +-4, 2.4 at +-6 (column 0).
6. Near-separability (measured): heat(cx, cz) ~ F(cx) G(cz) / norm with log error sd 0.17 (0.12 read noise + 0.12 true
   interaction). 17% of all columns reach 12 on the hottest line; ~5 rows per line reach 6.5.
7. Heat is set by the seed FAMILY (bits 0-19): classes sharing a family hit together (a 256-class tile of one family
   is worth ~69 random seeds, not 256), so heat is a statement about which low-bit families line up with the disc.

## What heat is

`heat40(cx, cz)` = P(a random world seed makes >= 40 of the 197 chunks in the r <= 8 disc around the chunk
slime) / 2.1e-5, estimated from N random seeds (`hotspot_scan --heat-survey`). A property of the LOCATION,
averaged over seeds. A chunk's slime test depends on seed + X(cx) + Z(cz): the X and Z terms are ADDITIVE,
so heat at (cx, cz) is a function of an X-difference vector and a Z-difference vector. That is what lets two
1-D scans (every row, every column) stand in for a 2-D scan, provided the interaction is measured.

## TODO (project owner, 2026-09-21): make phase 5 much faster WITHOUT losing data - later

Hard rule (see memory results-must-not-change): an optimization is accepted only if, on a test set measured
the unoptimized way, it misses ZERO additional true heat-12+ spots. Speed may cost precision on spots that are
clearly out; it may never cost recall. Candidates, most promising first:

1. **Sequential measurement (early stopping).** Measure in steps (e.g. 25k, 50k, 100k, 300k seeds) and stop a
   spot as soon as its running count proves it is far below 12 with a fixed tiny error (SPRT / a confidence
   sequence, error budget well under the 0.1% recall target). Most candidates sit near the model's margin,
   i.e. well below 12, and are decided in the first step. Expected 3-6x.
2. **Tighter prediction = fewer candidates.** Use all 4 reference rows AND columns, the residue (cx mod 65,536)
   and sister structure, and the measured line width to shrink the margin - accepted only through the same
   zero-leak validation. Every 10% off the margin cuts the candidate count a lot, since counts rise steeply
   toward low heat.
3. **Rows per line.** If phase 2 shows each line's best row is the same for every column (the separable
   picture says it should be), measure that row plus only the neighbours that can reach 12 - not a fixed band.
4. **Kernel work.** Check `countTail` exits as soon as a seed reaches T=40 or can no longer reach it; measure
   along a line with `--heat-survey` (one row, many columns, shared Z terms) instead of per-spot mode.
5. **Rare-event sampling (research).** heat is the probability of a rare event (>= 40 of 197 chunks). Drawing
   seeds preferentially from families the phase model says are rich at that location, then re-weighting, is
   unbiased and could cut the seeds needed per spot by a large factor. Must be validated against plain
   sampling before use.
6. **Precision pass is optional for completeness.** Recall comes from the generous first-read cutoff (7.5);
   the 3M re-measure only sharpens values near 12 - run it later, or only on spots that get hunted.
7. Hardware: the heat kernel is pure integer compute and should scale ~10x on a PRO 6000.
